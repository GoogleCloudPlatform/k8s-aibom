## Leg 2 — the same with the Dynamo operator scaled to zero

| UTC | Step | Result |
|---|---|---|
| 16:51 | `scale deploy/dynamo-platform-dynamo-operator-controller-manager --replicas=0`; webhook Service has no endpoints | — |
| 16:51–16:59 | Polled `AIBOMControllerConfig/default` every 30 s for 7 min 15 s | `Degraded=False` throughout; `aibom_watch_healthy{kind="DynamoGraphDeployment"}` and `…DynamoComponentDeployment` stayed `1`; no `WatchUnhealthy` event; no `watch degraded` log line |
| 16:52 | Existing DGD AIBOMs | both still present and Ready, hashes unchanged |
| 16:56 | New `apps/v1` Deployment (vLLM) in the same namespace | AIBOM within 20 s; controller 0 restarts |
| 16:52 | `kubectl apply` of a third DGD while the webhook is down | **rejected by the API server**: `conversion webhook for nvidia.com/v1alpha1, Kind=DynamoGraphDeployment failed: Post "https://dynamo-platform-dynamo-operator-webhook-service…": connection refused` |
| 17:01 | Direct reads while the webhook is down | `kubectl get dynamographdeployments.v1beta1.nvidia.com -A --chunk-size=1` **succeeds** (both DGDs listed); `GET /apis/nvidia.com/v1beta1/…/dynamographdeployments?limit=1` succeeds with and without `resourceVersion=0`; **`kubectl get …v1beta1… vllm-disagg` (single-object GET) fails** with the same conversion error |
| 16:59 | Operator scaled back to 1 | nothing to recover; watches never left healthy; the third DGD applied afterwards gets its AIBOM in 40 s |

What this means, stated plainly:

- **The API server keeps serving v1beta1 lists and watches from its per-version
  watch cache while the conversion webhook is down; only single-object GETs and
  all writes reach the webhook and fail.** So k8s-aibom's informer stays
  established and its steady-state probe (a `Limit=1` LIST through the uncached
  reader, Design 004) succeeds, which is why no `Degraded`/`WatchUnhealthy`
  signal appeared. During the outage the Dynamo API is effectively read-only:
  no DGD can be created, changed or deleted, so there is no change for the
  inventory to miss, and the last-known inventory remains correct.
- **The gap is observability, not correctness:** an operator reading the
  `AIBOMControllerConfig` conditions does not learn that the Dynamo kinds are
  running on cached reads. Filed as a follow-up: make the steady-state probe a
  single-object GET (take one name from the cached list, read it uncached), which
  this run shows does fail through the webhook. Targeted at 1.6.2.
- Watch-isolation itself held: the apps/v1 path, the other third-party kinds and
  the controller process were unaffected (0 restarts), which is what #127 set out
  to guarantee. The crash-loop and "zero AIBOMs" failure modes recorded in the
  #127 investigation did not occur.

## Leg 4 — steady-state cost with the DynamoGraphDeployment and DynamoComponentDeployment watches on

Window 17:02:28–17:17:37 UTC (900 s), operator up, present in the opted-in
namespaces: two DGDs (five + six Pending pods under grove), three vLLM
Deployments and one nginx control, all pinned to a non-existent node. Third-party
kinds watched: `DynamoGraphDeployment`, `DynamoComponentDeployment`,
`InferenceService` (pre-existing KServe CRD); LWS, DisaggregatedSet and
NIMService CRDs absent. Counters read from the controller's own `/metrics` over
`kubectl port-forward`, `kubectl top` for the working set.

| Measure | Value |
|---|---|
| `rest_client_requests_total` delta | 59 in 900 s = **3.9 requests/min** (48 GET, 11 PUT) |
| Reconciles in the window | 11, all fast-path (`inputs unchanged`) status touches, which are the 11 PUTs; the Dynamo operator and grove update DGD status while pods sit Pending, and each update re-enqueues the DGD |
| `aibom_watch_errors_total` delta | 0 |
| Process CPU over the window | 2.0 s = **2.2 mCPU average** (`kubectl top`: 3m throughout) |
| Memory | **28–34 MiB working set** (`kubectl top`); 61 MiB RSS |
| `aibom_watch_healthy` at the end | 1 for all three watched kinds |

Against the v1.6.0-rc.1 walk (3.26 requests/min with three present kinds and no
DGD) and the 1.5.1 baseline (0.96/min, zero writes at 1,002 workloads), the
difference is the 11 fast-path status writes driven by DGD status churn from a
graph whose pods never schedule; with running pods that churn stops. A
generation-change filter on third-party kinds would remove it entirely and is
noted for 1.7.

## Teardown (17:18–17:20 UTC)

Both DGDs deleted: their AIBOMs went with them by owner reference while the
two Deployments' AIBOMs stayed until their namespace was deleted. `helm uninstall`
of k8s-aibom left no Deployment, RBAC, ServiceAccount or `AIBOMControllerConfig`;
the two k8s-aibom CRDs were deleted by hand (the chart keeps them by design).
`helm uninstall dynamo-platform`, then its 14 `nvidia.com`/`grove.io` CRDs and the
namespaces. End state: zero Helm releases, zero PVCs, no run namespaces; CRDs
present are the pre-existing `inferenceservices.serving.kserve.io` and
`rayclusters.ray.io`, neither installed by this run. The `adr019-tmp` node pool
was deleted afterwards.
